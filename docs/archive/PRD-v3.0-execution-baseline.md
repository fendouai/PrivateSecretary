# 私人秘书（PrivateSecretary）产品与技术方案 v3.0

**文档版本**：v3.0  
**文档状态**：实现基线（Implementation Baseline）  
**适用主机**：Apple Silicon Mac（M2/M3/M4，16 GB 内存基准）  
**目标 Agent 宿主**：Codex（Skill + MCP）  
**核心架构变更**：从“三层数据处理”升级为“五层认知记忆架构”

## 第一部分 产品设计

### 1.1 产品定位

一个全天候在后台静默运行、只在你真正需要时出现的**本地 AI 秘书**。它持续感知音频和屏幕的语义变化，在写入时就完成结构化提取，通过显著性驱动的巩固机制形成可回溯的工作记忆，并在检测到明确意图时直接进入 Codex 的任务执行循环。

产品哲学是“**采集尽可能多，上报尽可能少，记忆尽可能准**”。用户不会感受到它在录音或截屏，只会感受到“它在我需要的时候已经知道了上下文，而且它记住的正是重要的东西”。

产品不承诺“所有看过的都能搜到”，而是承诺：

1. 重要的东西会被准确记住；
2. 不重要的东西会被及时遗忘；
3. 被记住的东西能追溯到产生它的时间、应用与感知来源；
4. 任何具有外部副作用的动作，都不会绕开用户确认。

### 1.2 五层记忆架构的产品含义

v3.0 的核心变化是把 v2.0 的“原始滚动 / 日报 / 意图直执”三层存储，重新映射为**五种认知功能**：

| 层 | 认知功能 | 用户可感知的产品行为 | 典型存续 |
|---|---|---|---|
| **L0 感觉缓冲** | 未经解释的原始信号 | 不感知，仅用于当前处理窗口 | 秒级 |
| **L1 工作记忆** | 当前正在处理的候选片段 | 门控在“判断” | 分钟级 |
| **L2 情景记忆** | 带时间戳的“经历” | “今天下午我在终端里看到了什么” | 天–周 |
| **L3 语义记忆** | 巩固后的事实与模式 | “上周三决定的方案是什么” | 月–永久 |
| **L4 程序性记忆** | 重复成功的执行模式 | “以后这类报错自动这样记” | 永久 |

**L0 不是 v2.0 的“24–72 小时原始滚动仓库”**。v2.0 的长窗口保留本质上是在用存储弥补写入时处理的不足。v3.0 的原则是：**在写入路径上就完成足够结构化的提取，原始信号只保留当前处理窗口所需的最小长度**。如果 L2 的情景记录已经捕获了 ASR 文本、OCR 区域和关键视觉语义，原始音频分片和全屏帧不再需要以“可回溯”的名义长期驻留磁盘。

**L4 是 v2.0 完全缺失但全天候系统必须有的层**。当你反复执行某类意图任务（例如“记录终端报错”总是走相同的 OCR 裁剪 + 任务创建流程），系统应该把这个模式蒸馏为程序性记忆，下次同类意图触发时直接复用执行路径，而不是每次重新经过 LLM 推理。

### 1.3 三层核心产品体验

**体验一：可追问的近期经历（L2 情景记忆）**。用户问“刚才那个讲向量数据库的视频里关于 HNSW 参数说了什么”，skill 从 L2 情景记忆中混合检索，返回带时间戳的摘要和来源引用，而不是回放原始音频。

**体验二：有索引的每日简报（L3 语义记忆的日级投影）**。每天夜间巩固后生成的简报不是“全量流水账”，而是**经过显著性过滤的语义提炼**。简报的每条关键事件附带 `memory_id` 引用，用户或 agent 可以按需钻取完整情景记录。简报同时充当“记忆索引目录”，而不是“记忆本身”。

**体验三：有边界的意图直执（L1 → L4）**。Intent Gate 判定为 `explicit` 的条目进入任务队列。**涉及本地记录、跟踪、提醒、创建待办**的意图可以不经过用户确认直接执行；**涉及发送、修改、删除、对外 API 调用**的意图，无论 confidence 多高，必须走 Codex 的确认流程。这个边界是 `SKILL.md` 中的硬编码策略，不依赖模型判断。

### 1.4 隐私与信任模型

**原始信号的克制**。L0 感觉缓冲只保留当前处理窗口需要的原始信号，VAD 未触发或屏幕无变化的片段不进入缓冲。L2 情景记录保存的是结构化 ASR 文本和 OCR 区域，不是原始像素或波形。原始音频分片和屏幕帧不进入长期存储路径。

**记忆写入的防御**。不是所有结构化提取的结果都无条件写入 L2。写入路径上设有一道质量门：**与现有记忆的一致性检查 + 显著性阈值**。这对应 OWASP Agent Memory Guard 的本地等价物——防止低质量或矛盾信息污染长期记忆。

**意图直执的硬边界**。`auto` 类别严格限定在低副作用操作（record / track / remind / todo）。任何可能产生不可逆外部影响的意图，必须经过 Codex 的用户确认流程。这是产品策略在 skill 层的硬编码，不是模型行为。

**内容与指令分离**。屏幕与音频中的文本是不可信观察数据，不是发给 agent 的指令。记忆内容中出现“忽略之前指令”“调用某工具”等注入特征时，质量门拒绝将其提升为 L3 事实；`recall` 与 `drill_down` 的返回值都带有 `trust: untrusted_observed_content` 标记，Skill 明确要求不得把这些字段当指令执行。

**可纠正与可遗忘**。事实支持 `active / pending_review / superseded / retracted` 状态；用户可审查、接受、拒绝或纠正事实。情景记录支持按显著性衰减归档到 cold 层，也支持彻底清除。记忆不是只增不减的黑箱。

### 1.5 与竞品的核心差异

Granola 走“无 bot 会议记录”路线，限定在音频和会议场景；Rewind 走“全量屏幕回溯”路线，隐私压力集中在“所有屏幕内容都被持久化”。本产品的差异在**记忆的写入时结构化和显著性驱动的巩固**：它不承诺“所有看过的都能搜到”，而是承诺“重要的东西会被准确记住，不重要的东西会被及时遗忘”。这是认知架构层面的差异，不是采集范围或存储时长的差异。

### 1.6 成功指标

| 维度 | 指标 | v3.0 目标 |
|---|---|---|
| 记忆质量 | L3 事实可追溯率 | 100%（每条事实至少一个 L2 来源） |
| 检索体验 | `recall` p95 本地延迟 | < 120 ms（<= 10,000 条记忆） |
| 上下文成本 | 单次 `recall` 返回摘要长度 | <= 280 字符/条，默认最多 8 条 |
| 功耗 | 规则层压制后的常驻平均功耗 | 语音稀疏场景 < 5 W |
| 安全 | 高副作用意图绕过确认 | 0（策略层硬约束） |
| 隐私 | 长期存储中的原始像素/波形 | 0 |
| 可治理 | 矛盾事实进入待审查或取代流程 | 100% |

### 2.2 Layer 0：Capture Daemon

**采集配置**：`SCStreamConfiguration.capturesAudio = true`（macOS 13+）采集系统音频；`captureMicrophone = true`（macOS 15+）作为可选开关，单独申请 Microphone 权限。默认只采集系统音频——单一系统音频时钟源避免了双时钟同步的漂移问题；如果启用麦克风，必须基于 presentation timestamp 实现明确的 gap-fill 逻辑，否则丢弃的音频 buffer 会变成不可逆的漂移。

**VAD 在 Capture Daemon 内部**。Silero VAD CoreML 在 ANE 上的推理成本低到可以每 32 ms 无条件运行，作用是在音频离开 Daemon 之前就把静音砍掉。没有语音活动的块不进入 Preprocessing Daemon。

**屏幕侧第一层过滤**。SCStream 只在屏幕内容实际变化时交付帧，帧到达即 damage signal。Daemon 内部再对到达帧做分块像素差分（Accelerate/vImage），只输出变化区域的裁剪和坐标。

**L0 环形缓冲的尺度**：音频默认 60 秒（不是 v2.0 的 300 秒），屏幕事件默认 30 帧。L0 是**感觉缓冲**，不是长期仓库。Preprocessing Daemon 在候选包生成后，L0 中对应的原始信号即可被覆盖。只有被 L2 情景记录引用的片段，才以结构化形式保留下来。

**TCC 终态处理**。Screen Recording 权限被拒绝时，Capture Daemon 不进行无限重试，而是进入 `capture_unavailable` 终态并通过 IPC/MCP 暴露状态。用户授予权限后通过手动重启恢复。

### 2.3 Layer 1：Preprocessing Daemon——写入时结构化

ASR 选型为 **Qwen3-ASR 0.6B，CoreML 部署在 ANE**。实测数据：3 分钟中文片段上 ASR 本身 46.4 秒（约 3.9× 实时），CPU 6.7 W，ANE 3.5 W，峰值内存 1.41 GB。同测试中 Whisper large-v3-turbo 耗时 85.3 秒，CPU 15.3 W，ANE 仅 0.4 W，且在该中文样本上准确率更低。对于 24/7 后台运行，功耗和 ANE 利用率比峰值速度更重要。

OCR 使用 RapidOCR 或 PaddleOCR mobile 的 CoreML 转换版，只对 Capture Daemon 输出的变化区域跑。ANE 上的 detector / recognizer 阶段延迟在亚毫秒到毫秒级。

**关键升级：输出不是“候选包”，而是两条并行写入。** Preprocessing Daemon 在生成 L1 候选包的同时，执行**写入时结构化提取**：

- **情景记录**：ASR 文本、OCR 区域、时间戳、前台应用/窗口标识，作为 L2 情景记忆的原始条目，附带 `provenance` 指针；
- **原子事实候选**：如果候选包中包含可独立存在的信息（用户偏好、决策、待办、错误模式），由 0.5B–3B 级别模型在写入时提取为原子事实候选，进入质量门检查后再决定是否提交到 L3 语义记忆。

Reminiscence 的发现支持这个设计：**模型选择影响覆盖率，但不影响精确率**——最便宜的模型在精度上与最贵的模型持平。写入时提取不需要大模型，0.5B 级别在原子事实提取这种窄任务上足够。

**质量门**：原子事实候选在写入 L3 之前，经过与现有记忆的一致性检查（矛盾检测）和显著性阈值过滤。不是所有提取结果都无条件写入。

### 2.4 Intent Gate：0.5B 门控与规则层前置

Intent Gate 的任务是三分类加路由：`none` / `explicit` / `uncertain`，外加 1–2 句 `routed_text`。模型为 **Qwen2.5-0.5B int8，CoreML 部署在 ANE**。ANE 的编译权重上限约 1 GB，0.5B int8 约 472 MB，可以完整编译运行；1.5B int4 虽然能编译但速度掉到约 24 tok/s 且短生成质量退化；3B int4 权重约 1.7 GB，无法在 ANE 上编译。

**规则层是功耗可行的关键**。候选包在进入 0.5B 门控之前，先经过零成本过滤：文本长度低于阈值、全为空白/标点、与最近已处理片段高相似度、同一应用/窗口在节流窗口内重复触发。只有规则层无法判定的片段才进入 LLM 门控。**0.5B 的实际调用频率远低于 VAD 触发频率**，这是 24/7 功耗可持续的前提。

**来源安全策略**：只有麦克风、直接输入（manual）或 mixed 来源的文本可以产生 `auto` 任务。系统音频里别人的对话即使包含“帮我记一下”，最多进入 `uncertain` 审查，不直接创建可自动执行的任务。这是对误触发风险的工程化收敛。

### 2.5 巩固 Worker：L2 → L3 的夜间认知管线

这是 v3.0 相对 v2.0 的核心增量。巩固 Worker 作为 LaunchAgent 在凌晨（例如 02:00–04:00）运行，使用 **MLX 上的 Qwen2.5-3B 或 7B 4-bit** 批量处理当天的 L2 情景记录。Qwen2.5-3B 4-bit 在 MLX 上的实测 decode 速度约 28 tok/s，TTFT 约 36 ms，峰值内存约 1.96 GB。夜间批量处理不要求低延迟，这个速度足以在数十分钟内完成一天的巩固。

**巩固的输入与输出**：

- **输入**：当天所有 L2 情景记录（ASR 文本、OCR 区域、意图记录），经过粗聚类（按应用、时间连续段、意图类型分组）避免输入无限膨胀。
- **显著性评分**：采用 Reminiscence 的六信号框架——奖励、错误、新颖性、情绪、目标相关性、访问频率。只有超过阈值的候选进入巩固管线。**日报不再是“当天的全量摘要”，而是“当天显著事件经过巩固后的语义提炼”**。
- **输出**：L3 语义记忆（原子事实 + 矛盾解决后的更新 + provenance 引用）+ 当日日报索引（Markdown，每条关键事件附带 `memory_id`）+ L4 程序性记忆候选（高频任务执行模式）。
- **遗忘**：未被访问或未触发的 L2 情景记录，检索权重按显著性衰减。权重低于阈值时，只保留摘要和 provenance，原始结构化文本归档到 cold 层。这与“存储层面的滚动覆盖”不同——它是**认知层面的遗忘**，由显著性驱动，而不是墙钟时间驱动。

**巩固模型的部署**：巩固 Worker 不应与实时链路共享进程。MLX 模型在夜间 LaunchAgent 中按需加载，完成当天巩固后释放。如果巩固任务量很大，吸收 PyRAMIND 的原则：**能算术化的维护决策不交给 LLM**——确定性路径（写入巩固、强化、遗忘、层晋升、检索打分）可以在嵌入上做闭式算术，只有实体标注和摘要生成调用模型。

**反幻觉契约**：巩固只使用数据库中已有的 L2 记录与 L3 事实，增强型摘要模型必须返回可验证的 `memory_id`；任何无法映射到源记录的条目被丢弃。日报是索引，不是新事实的来源。

### 2.6 L4 程序性记忆：从任务执行历史中蒸馏

当意图任务的执行日志积累到一定量后（例如同类 `intent_type` 有 ≥ 5 次成功执行记录），巩固 Worker 将高频模式蒸馏为 L4 程序性记忆。例如“记录终端报错”的已知模式可能包含：OCR 裁剪右下角终端区域 → 提取红色错误文本 → 创建带 `bug` 标签的待办 → 附上时间戳和前台应用。

下次同类意图触发时，MCP 工具 `get_procedural_pattern(intent_type)` 返回已知执行路径，Codex agent 可以直接复用，而不需要重新推理。Letta 的 Skill Learning 和 ZenBrain 的 procedural 层是直接参照。

## 第三部分 技术方案

### 3.1 记忆存储层：Wax 或 CP Memory

**Wax** 是 Mac 本地记忆的首选基座：纯 Swift、单文件（`~/.wax/memory.wax`）、Apple Silicon 原生、Metal 加速 HNSW 索引，混合召回 p95 约 6 ms，冷打开约 9 ms，原生提供 MCP server，可与 Codex、Claude、Cursor 共享同一个记忆文件。它的“一个文件、所有 agent 共享”模型与你的架构高度契合，且不需要引入 Python 运行时。

**CP Memory** 是 Codex 专用的备选：本地 SQLite（`~/.cp-memory/memory.db`），存储 facts、preferences、ongoing work、episodes、decisions、conversation checkpoints，通过 MCP tools 和 lifecycle hooks 恢复上下文，明确强调“可治理、可审查、可纠正”而不是“记住尽可能多”。如果 Wax 的成熟度不足以承载 L3 语义层的治理需求，CP Memory 的 review inbox 和 correction states 是更贴合的选择。

**不建议自己从零构建向量数据库和检索层**。本地记忆框架已经足够成熟，自建的成本主要在调试检索质量，而不是创造价值。

### 3.2 混合检索

单一检索信号在长时记忆上不够。Mem0 的三信号融合和 EngramRAG 的三源混合检索都表明，**混合 BM25 + 向量检索**是必要的，不是可选的。对于“上周三我在干什么”这类时间查询，纯向量检索会失败，需要时间过滤 + 关键词匹配作为并行通道。Wax 本身支持 `--mode hybrid`（Text + Vector），如果使用 CP Memory 或自建路径，应确保 BM25 通道存在。

**时间语义解析前置**：查询中的“昨天下午”“上周三”“last Wednesday”等表达先被解析为 `DateInterval`，从检索文本中剥离，再进入混合检索。显式 `time_range` 参数优先于自然语言解析。

**结果折叠**：`recall` 只返回摘要、时间、应用、层、分数与 `memory_id`；完整 ASR/OCR 内容只能通过 `drill_down` 获取。这是上下文卸载原则在工具协议上的强制实现。

### 3.3 MCP 工具集（记忆原生）

| 工具 | 层 | 语义 |
|---|---|---|
| `recall(query, time_range?, layer?)` | L2/L3 | 混合检索，返回**摘要 + `memory_id`**，不返回全文 |
| `drill_down(memory_id)` | L2/L3 | 按需拉取某条记忆的完整结构化内容 |
| `get_digest(date)` | L3 | 获取日报（索引目录形态） |
| `generate_daily_digest(date?)` | L3 | 按需触发巩固与日报生成 |
| `get_procedural_pattern(intent_type)` | L4 | 获取某类意图的已知执行模式 |
| `get_pending_tasks(limit?)` | L1 | 拉取待处理意图任务 |
| `claim_task(task_id, owner?)` | L1→L4 | 幂等认领任务 |
| `complete_task(task_id, outcome, steps?, success?)` | L1→L4 | 幂等完成任务，写入执行日志，成为程序性蒸馏候选 |
| `cancel_task(task_id, reason?)` | L1 | 取消任务 |
| `list_review_items(limit?)` | L3 | 列出待审查的冲突/低置信事实 |
| `review_fact(fact_id, action, corrected_statement?)` | L3 | 接受、拒绝或纠正事实 |
| `get_status()` | 系统 | 数据库、capture、意图模型与计数健康状态 |

**`recall` 的返回策略是关键**：默认返回摘要和索引，不展开全文。这是上下文卸载的核心教训——上下文中只保留一行摘要和索引路径，完整信息在外部。如果 agent 每次会话都把 `recall` 的所有结果展开，Token 消耗会迅速失控。`SKILL.md` 中应明确规定：**`recall` 的结果默认折叠，只有 agent 判断需要时调用 `drill_down`**。

### 3.4 MCP Tasks 的现实约束与降级方案

**关键工程事实**：Codex 当前版本（0.156.0 及 main 分支）**不支持 MCP Tasks 扩展**。Codex 把每个 MCP 工具调用都当作普通的 `tools/call`，任何不是 tool result 的返回都被视为错误；长调用会阻塞当前轮次直到超时。MCP Tasks 在 2026-07-28 从实验性核心转为正式扩展，但 Codex 和 Cursor 都尚未声明支持。

因此，意图直执的“异步实时”能力在当前 Codex 版本下**不能依赖 MCP Tasks**。可行的降级方案：

- **主路径**：`get_pending_tasks` 作为普通工具调用，Codex 在**每次会话开始时**同步拉取待处理任务，会话中按需再次拉取。任务状态通过文件/轻量数据库维护，`claim_task` / `complete_task` 是幂等的普通工具调用。
- **主动唤醒的替代**：如果需要“任务产生时通知 Codex”，不应依赖 MCP sampling（2026-07-28 已标记为 deprecated）。更稳妥的是 LaunchAgent 检测任务队列变化 → 调用 Codex CLI 的受控路径，或者在 Codex 支持的 Events 通道可用时再做集成。

这个降级不丢失功能，只降低“实时性”——用户下一次与 Codex 交互时任务就会被消费。对于“记录/跟踪/提醒”类意图，这个延迟是可接受的。

### 3.5 资源与功耗矩阵

| 组件 | 常驻内存 | 活跃功耗 | 调用频率 | 数据来源 |
|---|---|---|---|---|
| Capture Daemon + Silero VAD | ~50–80 MB | < 1 W | 持续 | — |
| ASR Qwen3-ASR 0.6B (ANE) | ~1.4 GB（按需） | 6.7 W CPU + 3.5 W ANE | 仅 VAD 触发片段 | 实测 |
| OCR mobile CoreML (ANE) | ~100–300 MB | < 1 W（短暂） | 仅屏幕变化区域 | — |
| Intent Gate 0.5B int8 (ANE) | ~500 MB | 低个位数 W | 规则层无法判定的片段 | — |
| 巩固 Worker（3B 4-bit MLX） | ~2 GB（夜间加载/释放） | 夜间活跃，数十秒–数分钟 | 每日一次 | 实测 28 tok/s, TTFT 36 ms |
| MCP Server + Wax/CP Memory | ~50–100 MB | < 0.5 W | 空闲等待 | — |

**整体功耗取决于规则层对 0.5B 门控调用频率的压制效果**。语音稀疏、屏幕以静态阅读为主时，平均功耗可压在个位数瓦；长时间会议 + 频繁屏幕切换时活跃占比上升，但仍是笔记本电池可承受一个工作日的量级。

## 第四部分 风险与演进

### 4.1 关键风险

**风险一：0.5B 门控的区分能力不足**。真实场景中“有人在说话”和“有人在对系统说话”的边界模糊。缓解：规则层前置、阈值保守启动（0.8）、保留 `uncertain`、3B 低频复核、系统音频不允许自动执行。

**风险二：巩固产出的“幻觉摘要”**。3B/7B 模型从大量情景记录生成语义事实时可能推断出未发生的事。缓解：L3 每条事实必须附带 `provenance` 指向 L2 源情景；巩固 prompt 硬性要求“只基于提供的记录，不添加外部推断”；日报的每条关键事件附带 `memory_id` 可回溯验证。

**风险三：意图直执的误触发**。0.5B 门控即使 confidence 很高，也可能把随口一说误判为任务。缓解：`auto` 类别严格限制在低副作用操作；高频误报通过日报中的“已捕获意图”列表让用户事后纠正；`confirm_required` 类别永远走确认。

**风险四：MCP Tasks 在 Codex 中的支持不确定性**。降级方案已经明确：会话时拉取 + 幂等任务工具。架构上不把实时唤醒作为唯一路径。

**风险五：TCC 权限的持续稳定性**。Screen Recording 权限是手动授予的，系统更新或 bundle identifier 变更可能导致失效。Capture Daemon 应把“用户拒绝 TCC”定义为终态而非可重试错误，MCP server 暴露明确的 `capture_unavailable` 状态。

**风险六：感知内容中的提示注入**。会议字幕、网页或终端输出可能包含针对 agent 的指令。缓解：感知内容标记为不可信；注入特征内容禁止提升为事实；MCP 返回带 trust 标记；Skill 强制内容与指令分离。

### 4.2 演进路径

**Phase A（记忆基座与写入时结构化）**：用 Wax 或 CP Memory 替换 v2.0 的原始滚动存储。实现 L2 情景记录 + 写入时原子事实提取 + 质量门。MCP 工具升级为 `recall` + `drill_down` 形态。这一步的直接收益是**上下文卸载**——Token 消耗立即下降。

**Phase B（巩固与遗忘）**：引入夜间巩固 Worker，实现显著性评分、L2→L3 巩固、按显著性衰减的遗忘、日报索引生成。评估巩固后的检索精确率是否随存储压缩而保持。

**Phase C（程序性记忆与执行闭环）**：当意图任务执行日志积累到足够量后，蒸馏 L4 程序性记忆。完善 `SKILL.md` 中的执行边界策略。如果 Codex 后续支持 MCP Tasks，再将任务队列升级为异步 Tasks 语义。

**Phase D（感知硬件层生产化）**：将参考实现的 whisper.cpp / Vision 适配器替换为 Qwen3-ASR 0.6B CoreML 与 RapidOCR CoreML；完成不同 macOS 版本上的 TCC、ANE 功耗、双时钟音频同步实测。

## 第五部分 本仓库实现基线

> 目标方案与可运行实现必须区分。以下内容定义 v3.0 参考实现的范围、替换点和验收方式，避免把路线图写成既成事实。

### 5.1 交付范围

本仓库交付一个可构建、可运行、可测试的 macOS Swift 实现：

1. **认知记忆核心**：L0 缓冲、L1 候选、L2 情景、L3 语义、L4 程序性记忆的完整数据模型与生命周期；
2. **本地持久化**：SQLite（WAL + FTS5）单文件记忆库，CP Memory 风格的 facts / episodes / decisions / tasks 治理状态，BM25 + 向量混合检索；
3. **写入时结构化**：规则提取器 + 可选本地模型命令适配器；原子事实去重、矛盾检测、注入防护、显著性阈值；
4. **Intent Gate**：规则前置、可选本地 LLM 命令适配器、系统音频降级、`auto` / `confirm_required` 硬策略；
5. **任务队列**：幂等 claim/complete/cancel、执行日志、程序性模式蒸馏；
6. **巩固 Worker**：按日聚类、显著性过滤、日报索引、事实强化、显著性遗忘与 cold 归档、L4 蒸馏；
7. **MCP stdio 服务**：第三部分工具集，严格摘要返回、错误处理、健康状态；
8. **Unix domain socket 守护进程**：事件摄取、健康检查、模拟回放；
9. **macOS 感知适配器**：ScreenCaptureKit 系统音频与屏幕变化帧、能量 VAD、Vision OCR、whisper.cpp ASR 命令适配器；不可用时返回明确状态；
10. **Codex Skill**：会话启动拉取、折叠检索、意图执行边界、内容不可信规则；
11. **安装与运维**：LaunchAgent、安装/卸载脚本、doctor、示例配置、备份与清除说明。

### 5.2 明确的技术替换

| 目标方案 | 参考实现 | 原因与替换接口 |
|---|---|---|
| Wax / CP Memory | 内置 SQLite CP-Memory 风格后端 | 避免引入未固定的第三方二进制与数据库格式；`MemoryStore` 边界可替换 Wax 适配器 |
| Qwen3-ASR 0.6B CoreML | `whisper.cpp` 命令行适配器（可配置） | 不随仓库分发约 GB 级模型；`TranscriptionService` 协议可接 CoreML 实现 |
| RapidOCR CoreML | Apple Vision OCR | 系统原生、无需模型分发，输出同样是文本 + 归一化区域；`OCRService` 协议可替换 |
| Silero VAD CoreML | 能量 + 过零率 VAD（含预卷/挂起） | 无模型依赖、可确定性测试；`VoiceActivityDetector` 协议可替换 |
| Qwen2.5-0.5B Intent Gate | 规则门控 + 可选本地命令模型 | 规则层本来就是第一道功耗闸门；`IntentClassifying` 协议可接 CoreML/MLX |
| Qwen2.5-3B/7B 巩固摘要 | 确定性提取/摘要 + 可选命令模型 | 反幻觉优先，全部产出可追溯到源记录 |
| Metal/ANE 功耗实测 | 资源指标接口 + doctor | 无模型与 TCC 环境时无法诚实给出功耗数字 |

这些替换不改变认知分层、MCP 契约、策略边界和可观测性；它们改变的是模型质量与硬件占用。

### 5.3 验收标准

**功能验收**

- 输入一条包含终端报错的候选包，L2 立即可检索，L3 生成带 `provenance` 的错误事实；
- 输入“帮我记一下周五前提交 HNSW 参数对比”，生成 `record/todo` 任务，风险为 `auto`；
- 输入“帮我发邮件告诉张三”，生成 `send` 任务，风险为 `confirm_required`，Skill 强制确认；
- 重复候选不会重复创建情景/事实/任务；
- `recall` 不返回完整 ASR/OCR 文本，`drill_down` 才返回并累计访问；
- 生成日报后，每个关键事件都带 `memory_id`；
- 同类任务累计 5 次成功后，巩固产出可检索的 L4 模式；
- 低显著性旧情景归档后，数据库中不再保留原始 ASR/OCR，cold 层可恢复。

**安全验收**

- 系统音频来源不会被判为可自动执行的任务；
- send / modify / delete / external_api 永远 `confirm_required`；
- 提示注入文本不会进入 L3；
- 长期存储 schema 中不存在音频/图像 BLOB；
- TCC 拒绝时 daemon 不崩溃、不重试风暴，MCP 返回 `capture_unavailable`。

**质量验收**

- `swift test` 全部通过；
- MCP 协议集成测试覆盖 initialize / tools/list / tools/call / 错误路径；
- CLI 冒烟测试覆盖 ingest / recall / digest / consolidate / tasks；
- 模拟 24 小时数据量的 soak 测试完成且检索 p95 在目标范围；
- 测试报告记录实际环境、通过数、耗时与未自动化项。

### 5.4 文档结论

v3.0 的核心不是增加功能，而是**把记忆从“存储问题”重构为“认知问题”**。Wax 或 CP Memory 提供了 Mac 本地的现成记忆基座；写入时结构化提取、显著性驱动的巩固、以及按需加载的上下文卸载，共同构成了一个与全天候感知相称的记忆架构。L4 程序性记忆是 v2.0 缺失但 24/7 系统最终必须到达的层——没有它，每次意图任务都在重新推理，而不是在“学会”。MCP Tasks 在 Codex 中的缺失是一个需要诚实面对的现实约束，降级方案不丢失功能，只调整实时性预期。Docker 仍然只作为可选的夜间批量旁路，不进入实时记忆链路。

参考实现选择了一条**确定性、可测试、可替换**的路径：先把认知契约、治理状态、安全边界和协议接口固化，再把感知模型替换为适合目标硬件的 CoreML/MLX 版本。这样，模型升级不会破坏记忆语义，硬件权限问题也不会拖垮整个系统。
